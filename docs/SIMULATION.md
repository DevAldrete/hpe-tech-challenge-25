# Simulation Guide - Project AEGIS

**Version:** 2.1.0  
**Scope:** Runtime behavior that exists in current codebase  
**Last Updated:** 2026-03-08

## What Is Being Simulated

AEGIS simulation models the operational loop of a mixed emergency fleet:

- per-vehicle telemetry generation at fixed tick rates,
- dispatch and mission state transitions,
- failure progression and predictive alerting,
- maintenance/repair and return-to-service behavior,
- emergency lifecycle deadlines and auto-resolution/dismissal rules.

## Vehicle Tick Logic (Most Important Runtime Loop)

Implemented in `src/vehicle_agent/agent.py` (`VehicleAgent._tick`), each cycle runs in this order:

1. Failure scheduler may activate a scenario (unless in maintenance).
2. Repair timer is evaluated if vehicle is already in `MAINTENANCE`.
3. Baseline telemetry is generated by `SimpleTelemetryGenerator`.
4. Active failures mutate sensor values via `FailureInjector`.
5. Anomaly analysis runs (rule-based warmup, then ML predictor).
6. Critical alerts with active failures can push vehicle into maintenance.
7. Telemetry is published.
8. Alerts are published.

This ordering is deliberate: alerts are produced from post-failure telemetry, not baseline telemetry.

## Movement and Navigation

### Default movement behavior

- Geometric movement is the default strategy.
- Vehicles in `EN_ROUTE` move toward emergency coordinates every tick.
- Arrival condition (`speed_kmh == 0` at target) triggers `ON_SCENE` transition.

### Provider abstraction

Navigation is pluggable via `NavigatorProvider` in `src/vehicle_agent/navigation.py`:

- `geometric`: lightweight straight-line simulation (default and most stable).
- `osmnx`: optional road-network routing.

If `osmnx` routing fails, runtime falls back gracefully so the simulation remains live.

## Failure Simulation Model

`src/vehicle_agent/failure_injector.py` applies time-progressive degradation relative to vehicle-type baselines:

- `ENGINE_OVERHEAT`: temperature rises over time.
- `BATTERY_DEGRADATION`: voltage drops over time.
- `FUEL_LEAK`: fuel decreases quickly.
- `OIL_PRESSURE_DROP`: pressure declines over time.
- `VIBRATION_ANOMALY`: vibration rises over time.
- `BRAKE_DEGRADATION`: pad thickness decreases over time.

Multiple active scenarios can compound telemetry effects in a single tick.

## Predictive Alert and Maintenance Loop

1. Alerting pipeline analyzes mutated telemetry.
2. Alert events are published on alerts channel.
3. If severity is critical and failures are active, agent enters `MAINTENANCE`.
4. Repair duration is randomized around a base duration.
5. On completion, failures are deactivated and status returns to `IDLE`.
6. Agent publishes `alerts_cleared`; orchestrator retries queued dispatches.

This creates a realistic outage/recovery cycle without manual intervention.

## Emergency Simulation Behavior in Orchestrator

Orchestrator logic in `src/orchestrator/agent.py` + `src/orchestrator/emergency_service.py` simulates incident progression:

- nearest-available unit dispatch by type,
- dispatch acknowledgment tracking,
- arrival-based transition to `IN_PROGRESS`,
- coordination task progression by emergency type,
- automatic resolve/dismiss rules from simulated elapsed time.

## Time Modes

### Real-time

- Uses `RealClock`.
- Tick sleeps are wall-clock delays.

### Deterministic fast-forward

- Uses `FastForwardClock`.
- Tests and API-driven simulation can advance virtual time explicitly.
- Enables long mission/failure scenarios in seconds.

## API-Driven Fast-Forward Runtime

`src/orchestrator/api.py` configures a shared fast-forward clock in lifespan startup:

- orchestrator and background generators share the same simulation clock,
- a driver advances simulated time in regular real-time intervals,
- timeline/analytics endpoints reflect simulated timestamps.

## Current Limits and Known Simplifications

- Dispatch ETA uses average-speed heuristics, not live traffic.
- Geographic movement is primarily geometric unless optional provider is enabled.
- Control loop and persistence are co-located process concerns (no distributed job queue in critical path).

These simplifications are intentional to keep deterministic behavior and fast execution for challenge scope.
